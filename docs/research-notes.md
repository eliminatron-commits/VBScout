# Research notes (sources for the rule catalog and marketing)

Collected facts with their sources and the date they were checked. Everything that ends up in the rule catalog
(`rules/catalog.json`), reports or marketing must cite a source from here (or a newer one) with its date. Timeline
statements are always "expected"/"approximately" – Microsoft may move them.

> Access note (2026-09-26): the build environment's egress policy blocks learn.microsoft.com,
> techcommunity.microsoft.com and devblogs.microsoft.com. The statements below were checked through search-engine
> excerpts of these pages on 2026-09-26. Re-read the primary pages before a public release (release checklist).

## Office / VBA (phase 3)

| Fact | Source | Checked |
|---|---|---|
| VBA projects are affected in two ways: "any code that calls and executes external .vbs files will no longer be supported once VBScript is disabled or removed, and references to the VBScript type library for regular expressions will break". The collector rates both `breaks` (`VBS-621`, `VBS-601`), also `CreateObject("VBScript.RegExp")`, which needs the same library. | Microsoft 365 Developer Blog – [Prepare your VBA projects for VBScript deprecation in Windows](https://devblogs.microsoft.com/microsoft365dev/how-to-prepare-vba-projects-for-vbscript-deprecation/) (2025-09-10), via search excerpts | 2026-09-26 |
| Office Version 2508 (Build 19127.20154) and later include `RegExp`, `Match`, `MatchCollection`, `SubMatches` natively in VBA – no reference to vbscript.dll needed. `New RegExp` without the VBScript reference is therefore no finding; the reference itself is (a missing reference stops the whole project from compiling). | same | 2026-09-26 |
| The Microsoft Script Control (`msscript.ocx`, `MSScriptControl.ScriptControl`) runs code in the language of its `Language` property – VBScript or JScript; the property is empty by default. Third-party tutorials show `"VBS"` as an accepted name for VBScript. `Language = "VBScript"`/`"VBS"` → `VBS-611` (`breaks`); a language the code does not name → `VBS-612` (`review`); JScript → no finding. | Microsoft Learn – [Adding a ScriptControl](https://learn.microsoft.com/en-us/previous-versions/visualstudio/visual-studio-6.0/aa227400(v=vs.60)) (Visual Basic 6.0 documentation); helloacm.com tutorial on the Script Control, via search excerpts | 2026-09-26 |
| `execScript` of an HTML document window (`CreateObject("htmlfile").parentWindow.execScript code, language`) runs code in the given language; "the language defaults to JScript". VBA uses it where the Script Control is missing (64-bit Office). `"VBScript"` → `VBS-611`, a language from a variable → `VBS-612`, no language or JScript → no finding. | Microsoft Learn – [execScript method](https://learn.microsoft.com/en-us/previous-versions/windows/internet-explorer/ie-developer/platform-apis/aa741364(v=vs.85)), via search excerpts | 2026-09-26 |
| Microsoft names neither the objects of the Windows Script Host (`WScript.Shell`, `wshom.ocx`) nor the Scripting Runtime (`scrrun.dll`: `FileSystemObject`, `Dictionary`) as affected; a Microsoft Q&A question asking which files are affected has no official answer. Third-party reports: JScript still runs with cscript/wscript after the VBScript feature is removed. Decision: WSH objects → `VBS-632` (`review`, as the product specification asks); the Scripting Runtime is not reported (it would bury real findings and is not part of VBScript). | Microsoft Q&A – [What files, libraries, ocx, exe, … are impacted by the deprecations of VBScript?](https://learn.microsoft.com/en-us/answers/questions/1626472/what-files-libraries-ocx-exe-are-impacted-by-the-d); Windows OS Hub, Eleven Forum and DevHut (search excerpts) | 2026-09-26 |
| VBA project format: storage with `PROJECT` (text, protection fields `CMG`/`DPB`/`GC` obfuscated by "data encryption", 2.4.3), `PROJECTwm`, and `VBA` with the compressed `dir` stream (references, modules, `MODULEOFFSET`) and one stream per module (compiled code, then the compressed source). "Lock project for viewing" sets the protection state and the password hash – the source stays compressed, not encrypted, so the collector reads it and adds `projectLocked`. | Microsoft Learn – [[MS-OVBA]: Office VBA File Format Structure](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-ovba/575462ba-bf67-4190-9fac-c275523c75fc) (compression 2.4.1, data encryption 2.4.3), via search excerpts; checked against real files (Apache POI test data: their protection values decode to "no password"; unit test `protection_fields_are_decrypted`) | 2026-09-26 |
| Some files carry a wrong `MODULEOFFSET` (the source sits elsewhere in the module stream); Apache POI then searches the stream for a compressed container starting with `Attribute` – the collector does the same (POI test file 60279.doc, which oletools cannot read). | Apache POI – [`VBAMacroReader.java`](https://github.com/apache/poi/blob/trunk/poi/src/main/java/org/apache/poi/poifs/macros/VBAMacroReader.java) (`findCompressedStreamWBruteForce`) and `TestVBAMacroReader` | 2026-09-26 |
| Office Open XML with a password to open is a compound file with `EncryptionInfo` (version 4.4 agile, x.2 standard, x.3 extensible) and `EncryptedPackage` – the macros are inside the encrypted package → `VBS-600` (`passwordProtected`); rights management (`DRMEncryptedTransform`) → `encrypted`. Files encrypted with Excel's default password ("VelvetSweatshop") are reported the same way. | Microsoft Learn – [[MS-OFFCRYPTO]: Office Document Cryptography Structure](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-offcrypto/3c34d72a-1a61-4b52-a893-196f9157f083), via search excerpts; real encrypted files from oletools and Apache POI | 2026-09-26 |
| Binary Excel/Word files with a password to open encrypt the workbook/document streams only (`FilePass` record after the first `BOF`; `fEncrypted` in Word's file information block); their VBA storage stays readable. | msoffcrypto-tool (decrypts only those streams); real files from oletools (`encrypted.xls`/`.doc`) and Apache POI (`password.xls`, `xor-encryption-abc.xls`) | 2026-09-26 |
| Access keeps VBA in system tables: `MSysAccessStorage` (Access 2002 and later: rows of storages/streams, the project at `VBA/VBAProject`), `MSysAccessObjects` (Access 2000: a compound file in 3992-byte rows, row 0 = header with the length) and `MSysModules2` (Access 97, own format; code modules have types 0x8000 form, 0x8004 report, 0x8007 module). Page, row, long-value and usage-map layout; "encoded" Jet databases use RC4 per page (key in the obfuscated header, XOR page number); ACE databases with a password cannot be read. | mdbtools – [`HACKING.md`](https://github.com/mdbtools/mdbtools/blob/master/HACKING.md), `src/libmdb/file.c`, `write.c` (`mdb_crack_row`); Jackcess – `JetFormat.java`, `TableImpl.java`, `DataType.java` (`BIG_BINARY` for MSysAccessObjects), `DefaultCodecProvider.java`; checked against Jackcess and mdbtools test databases (Access 97–2016) | 2026-09-26 |

## Windows' own data under candidate names (found by the CI full scans, phase 3)

| Fact | Source | Checked |
|---|---|---|
| The component store (`%windir%\WinSxS`) keeps forward differentials (`f\`), reverse differentials (`r\`) and null differentials (`n\`, a new file "just compressed", applied to an empty buffer) next to the full files; Windows rebuilds a file from them when it installs or rolls back an update. The CI full scans (Windows Server 2022 and 2025) found such files named `slmgr.vbs` and `*.lnk` – reported as a VBScript file (`VBS-101`) and as corrupt shortcuts before phase 3's fix. They are no finding now; the real file is checked where Windows puts it. | Microsoft Learn – [Windows Updates using forward and reverse differentials](https://learn.microsoft.com/en-us/windows/deployment/update/psfxwhitepaper) (also Microsoft Download Center, id 57458), via search excerpts; wumb0 – [Extracting and Diffing Windows Patches in 2020](https://wumb0.in/extracting-and-diffing-ms-patches-in-2020.html) | 2026-09-26 |
| Differentials are MSDelta data: signature `PA30` (newer servicing stacks also `PA31`), then the target's file time (64-bit, 100 ns since 1601), then a bit stream; in updates and the component store a CRC-32 precedes the signature. The collector requires control bytes in that file time, so a script starting with "PA30" is not taken for a differential. | smilingthax – [MSDELTA / PA30 patch file format](https://github.com/smilingthax/msdelta-pa30-format); wumb0 – [`delta_patch.py`](https://gist.github.com/wumb0/9542469e3915953f7ae02d63998d2553) (PA19/PA30/PA31, CRC prefix); Cobalt – [Decoding Windows CBS Manifests: Reversing the DCM/PA30 Delta Format](https://www.cobalt.io/blog/decoding-windows-cbs-manifests-reversing-the-dcm/pa30-delta-format) | 2026-09-26 |
| Payloads of components that are not installed are kept compressed with the signatures `DCN`, `DCM`, `DCS`, `DCD` and version byte 1 (e.g. `Devices.mdb` of the DSC pull server, which the full scans reported as an unknown Office format, and scripts of features that are not installed – IIS legacy scripts such as `adsutil.vbs`, WSUS – reported as VBScript files). CI run 36279662753: with the recognition, 16 (Server 2025) and 35 (Server 2022) such findings are gone and none is new. | hfiref0x – [SXSEXP: Expand compressed files from WinSxS folder](https://github.com/hfiref0x/SXSEXP) | 2026-09-26 |
| User Access Logging (Windows Server) keeps `Current.mdb`, `SystemIdentity.mdb` and `<GUID>.mdb` in `%windir%\System32\LogFiles\Sum` – Extensible Storage Engine databases, not Access databases; Windows keeps them locked while it runs. ESE files carry the signature 0x89ABCDEF at offset 4 → no finding. A locked `Current.mdb` cannot be read at all and stays "not checkable (locked)" – the collector does not skip files by their path. | CrowdStrike – [How to Leverage User Access Logging for Forensic Investigations](https://www.crowdstrike.com/en-us/blog/user-access-logging-ual-overview/); svch0st – [Windows User Access Logs (UAL)](https://svch0st.medium.com/windows-user-access-logs-ual-9580f1100635); libyal – [Extensible Storage Engine (ESE) Database File (EDB) format](https://github.com/libyal/libesedb/blob/main/documentation/Extensible%20Storage%20Engine%20(ESE)%20Database%20File%20(EDB)%20format.asciidoc) (signature `ef cd ab 89` at offset 4) | 2026-09-26 |
